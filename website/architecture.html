Engineering & Audio DSP

Under the Hood: Multiplatform Audio & Sync Architecture

How Anchor achieves sample-accurate timing, unclipped first beats, and hardware playhead synchronization across Android, iPhone, and Windows.

55ms Sub-LSB Hardware Warmup & Output Standby

When OS audio sinks transition from idle to active playback, system mixers and DAC/amplifier circuitry take 25ms to 50ms to wake from low-power sleep states. If Beat 1's transient is written immediately without preparation, the hardware wake-up clips or completely swallows the first click.

Anchor solves this across all three platforms with a unified two-stage strategy:

  • Android (MetronomeAudioEngine): AudioTrack with Fast Path streaming at the native rate on a THREAD_PRIORITY_URGENT_AUDIO thread. Standby writes inaudible ±1 LSB dither (-90.3 dBFS) while the app is active, so Play aligns Beat 1 in the next ~5ms chunk. Cold starts run a 55ms warmup.
  • iOS (IosAudioEngine): AVAudioEngine + AVAudioPlayerNode with a dedicated high-priority thread keeping four 256-frame buffers queued ahead. Standby keeps the engine active with the player node stopped; Play queues Beat 1 and calls play() with zero start-up delay.
  • Windows (DesktopAudioEngine): javax.sound.sampled.SourceDataLine on a maximum-priority thread with 64-bit longFramePosition playhead tracking. Standby writes dither while the app window is open so Beat 1 starts instantaneously.
  • Zero Audio-Thread Allocations: All click voices (Tick, Click, Woodblock, Cowbell, Beep, Hi-Hat) are pre-rendered into static ShortArray PCM buffers. The real-time loop performs zero garbage collection or object allocations.

DelayCompensationEngine

Playhead-Anchored Synchronization Across Every Device

Why Anchor anchors visual and haptic scheduling directly to the hardware audio playhead on every platform instead of write buffers or OS sleep timers.

Hardware Playhead

Never Write-Head Anchored

Buffer write operations block based on hardware buffer size, causing write-triggered visuals to fire early and drift. Anchor polls the monotonic hardware playhead (AudioTrack.getPlaybackHeadPosition() on Android, AVAudioPlayerNode sample time on iOS, and SourceDataLine.longFramePosition on Windows) so 0ms offset matches the exact frame leaving the DAC.

-200ms to +300ms

Bidirectional Frame Offsets

Millisecond offsets for Visual/Screen Flash, Vibration, and Bluetooth audio convert directly into sample-frame deltas. Negative values fire cues early to compensate for display or vibration motor latency; positive values delay visual cues for high-latency external speakers.

Unified Visual Snap

Zero Fade-In Lag

The beat indicator bar, pendulum phase, and full-screen flash overlay share the same flashDelayMs schedule and trigger via instant state snap on beat onset before smoothly decaying.

Bluetooth Detection

Automatic Route Shift

Automatically queries active audio output routing (Bluetooth A2DP, BLE, or SCO on Android and iOS; device name matching on Windows) and applies the Bluetooth compensation offset only when wireless audio is actively routed.

Background Playback

System Media & Remote Controls

Keeps ticking while practicing with sheet music: Android mediaPlayback foreground service with MediaSession notification controls, iOS Now Playing with remote commands on Lock Screen and Control Center, and window-wide keyboard shortcuts on Windows.

Cross-Platform Core

100% Platform-Agnostic Logic

All state, domain models, synthesis, timing, slew-limited BPM adjustments, and accent memory reside in pure Kotlin Multiplatform (shared/src/commonMain). Each platform layer does only OS calls and UI hosting, guaranteeing identical musical behavior everywhere.

Kotlin Multiplatform: Android + iPhone + Windows

Codebase Structure

All application logic lives once in the shared Kotlin Multiplatform module. Android and Windows (x64 + arm64) share one Compose Multiplatform UI (sharedUi), the iPhone app uses SwiftUI, and every app contains only platform I/O on top of the shared core. Windows runs on the JVM desktop target, since Kotlin/Native has no Windows-on-ARM target.

  • Shared core (shared/src/commonMain): domain models, DelayCompensationEngine, TapTempoCalculator, ClickSynthesizer, the MetronomeSequencer warmup/sequencing/playhead-dispatch core, AudioRouteSelector, KeyValueSettingsRepository, ReleaseVersioning, and the MetronomeController state holder used by every platform.
  • Android audio (MetronomeAudioEngine.kt): AudioTrack Fast Path I/O on a THREAD_PRIORITY_URGENT_AUDIO thread, device routing, and the 32-bit hardware playhead. While the app is on screen the track stays open in output standby (inaudible dither), so Play places Beat 1 in the next ~5 ms chunk instead of re-creating the track and waking the hardware.
  • iOS audio (IosAudioEngine.kt): AVAudioEngine + AVAudioPlayerNode with a high-priority loop that keeps four 256-frame buffers scheduled ahead of the player-node playhead. While the app is in the foreground the engine keeps running with the player node stopped (output standby), so Play only queues Beat 1 and starts the player node.
  • Windows audio (DesktopAudioEngine.kt): javax.sound.sampled SourceDataLine on a max-priority thread with the 64-bit longFramePosition playhead and output standby; tested and packaged as per-architecture MSIs on Windows x64 and arm64 in CI (desktop.yml).
  • Shared Compose UI (sharedUi): the same MetronomeScreen renders on Android and Windows; platform differences (Material You colors, system bars, vibration settings) sit behind small expect/actual hooks.
  • System media controls: Android foreground mediaPlayback service with MediaSession notification controls; iOS Now Playing info and remote commands on the Lock Screen and Control Center.
  • Platform storage, haptics & updates: SharedPreferences / NSUserDefaults / java.util.prefs (Windows), VibrationEffect / UIImpactFeedbackGenerator, HttpURLConnection / NSURLSession / java.net.http (Windows, per-architecture MSI selection) — each behind a shared contract.
  • UI hosts: MetronomeViewModel (Android, @JvmOverloads AndroidViewModel) and MetronomeStore (SwiftUI ObservableObject) both host the shared MetronomeController.
